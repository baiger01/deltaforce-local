# Client Data Rules

These rules apply to all work in this project.

- The sole canonical development and runtime workspace is this repository root on `main`. Develop lobby, equipment, maps, match sessions and gameplay here, following the current domain directory layout. The user retired the old map worktree on 2026-10-22; historical evidence is not an alternate runtime or a source to merge automatically. Preserve current uncommitted changes and coordinate edits to shared modules. Use project-relative paths and `DF_LOCAL_SOURCE_GAME` / `DF_LOCAL_SHADOW_GAME` for configured installations; never require the original development computer's directory layout.
- The user explicitly authorized integrating the archived runtime on 2026-10-22. All restored and future features must be integrated here, with imports, configuration and launch wiring included. Use `work/run_local_game.py` for combined lobby/map validation; a lobby-only launch must be labeled explicitly. Do not leave functional implementations in another checkout or imply that copying code proves native acceptance.

- Research the installed client and the migration bundle before changing item or protocol mappings. Prefer extracted PAK tables, parsed Lua, protocol definitions, and actual client requests/logs.
- Do not invent client template IDs, receiver IDs, preset IDs, merchant/exchange IDs, enum values, asset paths, container layouts, durability, or weapon/ammunition relationships.
- Every permanent mapping must identify its source table/file and a row, function, serialized offset, or captured observation. Retain source hashes when extracting catalogs.
- Temporary interface probes must be explicitly marked as diagnostic and must not become permanent account or purchase data. Replace or remove them when client evidence is available.
- Preserve client-specified inventory destinations. An unknown configuration requires further research; do not silently redirect purchases or infer a layout from occupied cells.
- Local instance IDs (`gid`) and order IDs are generated by the local service. Keep them distinct from client template/configuration IDs and enforce their uniqueness.
- Treat tests as implementation checks, not proof of client data. Verify material protocol/display changes against the native client with logs enabled.
- Read the installed game without modifying it. Run native trials from the independent shadow, use a 1800-second observation period per the user's latest instruction, and verify SDK restoration afterward.

## Completion and Continuity

- Continue authorized unfinished work while meaningful progress remains possible. Passing unit tests, packet ACKs, object creation and visible icons are intermediate evidence, not native gameplay acceptance.
- Before every game launch, state whether it is diagnostic sampling or repair validation, what will be inspected, and what remains incomplete.
- Freeze executable trial sources during the corresponding native trial. Verify owned-process cleanup and SDK/configuration restoration before changing the next trial's runtime sources.
- Preserve fixes made by other collaborators. The user's latest report says sprint was repaired elsewhere; confirm the canonical implementation before relying on older reports that still call it broken.
